# 🔄 AI 功能迁移工作流

[English](./README.md) | [中文](./README.zh-CN.md)

> 一个基于 AI 的、人工审核的跨项目功能语义迁移工作流。

本项目用于解决：

> 不同项目之间的功能迁移问题。

重点在于：

- 保留目标项目架构
- 避免 AI 盲目复制代码
- 保持平台与基础设施差异
- 实现“业务逻辑迁移”而不是“代码硬拷贝”

---

# 📌 问题背景

传统功能迁移通常存在以下问题：

- 两个项目架构不同
- AI 无法同时理解两个项目
- 基础设施不一致
- 工具类不同
- 平台逻辑不同
- 隐式依赖难发现

常见问题：

- 缺少依赖
- 框架适配错误
- API 不兼容
- Bean 注入失败
- Runtime 异常
- AI 幻觉调用不存在的方法

本工作流通过：

- 双项目 AI 协作
- 人工上下文传递
- 语义级依赖分析
- 架构兼容性验证
- 本地化适配迁移

来降低迁移风险。

---

# 🎯 核心思想

```text
AI 无法同时完整理解两个项目。

因此：
- 源项目 AI 负责理解业务逻辑
- 目标项目 AI 负责理解目标架构
- 人类负责在两个 AI 之间传递上下文
```

这形成了一种：

```text
Human-in-the-loop semantic feature migration
（人工参与的语义级功能迁移）
```

---

# 🏗️ 工作流架构

```text
源项目 AI
    ↓
功能与依赖分析
    ↓
人工传递上下文
    ↓
目标项目 AI
    ↓
能力与兼容性验证
    ↓
人工传递结果
    ↓
源项目 AI 完善迁移方案
    ↓
目标项目 AI 执行适配迁移
    ↓
编译与测试
    ↓
审计与验证
```

---

# ✅ 适用场景

适用于：

- 老系统 → 新系统
- 单体 → 微服务
- Android → HarmonyOS
- Java → Kotlin
- SaaS → 私有化部署
- 项目间功能复用
- OEM 客户定制
- 中台能力抽离

---

# ❌ 不适用场景

不建议用于：

- 简单工具类复制
- 小型独立函数
- 普通 git merge
- 纯前端组件复用
- 架构完全一致的项目

这些情况直接复制通常即可。

# 🚀 标准迁移流程

---

# 第一步：源项目分析

## 🎯 目标

分析源功能：

- 核心业务逻辑
- 依赖链
- 工具类
- 基础设施耦合
- 风险点
- 目标项目需要具备的能力

---

## 💬 Prompt 示例

```text
我现在要迁移 XXXXX 功能。

核心文件：
- XXXService.java
- XXXManager.java
- XXXController.java

请分析：
1. 功能迁移注意事项
2. 迁移方案
3. 需要迁移的文件
4. 涉及的工具类与辅助方法
5. 基础设施依赖
6. 需要目标项目确认的内容

对于需要目标项目确认的地方，请向我提问。
```

---

# 第二步：目标项目能力验证

## 🎯 目标

验证目标项目是否具备：

- 等效工具类
- 基础设施支持
- 相同框架能力
- 替代实现
- 所需架构能力

---

## 💬 Prompt 示例

```text
我需要把 XXXXX 功能迁移到当前项目。

源项目分析后，需要确认：

- Redis 工具支持
- MQ Producer 实现
- UserContext 工具
- 权限框架
- 事务封装

请帮我确认：
1. 当前项目是否存在这些能力
2. 是否有替代实现
3. 是否存在架构差异
4. 是否有迁移风险
```

---

# 第三步：完善迁移方案

## 🎯 目标

将目标项目的反馈重新提供给源项目 AI。

这样源项目 AI 可以：

- 修正错误假设
- 适配目标架构
- 完善迁移方案
- 输出更安全的迁移策略

---

## 💬 Prompt 示例

```text
这是目标项目确认结果：

- Redis → Spring Cache
- MQ → RocketMQ
- 没有 UserContext
- 权限框架不同

请输出：
1. 最终迁移方案
2. 文件映射关系
3. 替代方案
4. 风险分析
5. 目标项目适配建议
```

---

# 第四步：目标项目适配迁移

## 🎯 目标

由目标项目 AI 执行“本地化适配”。

不是简单复制。

目标 AI 需要：

- 适配代码风格
- 适配架构
- 替换不兼容基础设施
- 保持目标项目规范
- 融合现有实现方式

---

## 💬 Prompt 示例

```text
请将 XXXXX 功能迁移到当前项目。

迁移方案：
[粘贴迁移方案]

目标文件位置：
[粘贴大致位置]

要求：
1. 适配目标项目架构
2. 保留目标项目规范
3. 替换不兼容依赖
4. 禁止直接复制粘贴迁移
```

---

# 第五步：编译与测试

## 🎯 目标

建立快速反馈循环。

检查：

- 缺少依赖
- Bean 注入失败
- 编译错误
- API 假设错误
- Runtime 不兼容

---

## 推荐命令

```bash
mvn test
```

或：

```bash
gradle test
```

---

# 第六步：迁移审计

## 🎯 目标

防止 AI 幻觉与隐藏回归。

重点审计：

- 核心业务方法
- 条件逻辑
- 权限逻辑
- 事务边界
- Cache 行为
- MQ 行为
- Error handling
- fallback 逻辑

---

## 💬 Prompt 示例

```text
请对比迁移后的实现与源实现。

重点检查：
1. 业务逻辑是否一致
2. 条件分支是否一致
3. 错误处理是否一致
4. 事务行为是否一致
5. Cache/MQ 行为差异
6. 是否遗漏边界情况
```

---

# 🛡️ 迁移边界规则

必须明确：

## 应该迁移什么

例如：

- 业务逻辑
- 校验逻辑
- 计算逻辑
- 核心流程

---

## 不应该迁移什么

例如：

- UI 实现
- 基础设施层
- ORM 实现
- MQ 实现
- Cache 实现
- 鉴权框架
- 平台专属代码

---

# 📑 依赖分类

推荐 AI 输出结构：

| 依赖类型 | 示例 | 处理方式 |
|---|---|---|
| 必须依赖 | UserService | 必须迁移 |
| 可替换工具 | RedisUtil | 替换 |
| 平台组件 | Android Context | 跳过 |
| 基础设施耦合 | Kafka | 适配 |
| 可选功能 | Metrics | 可选 |

---

# 📊 兼容性矩阵

示例：

| 能力 | 源项目 | 目标项目 | 处理方式 |
|---|---|---|---|
| Cache | Redisson | Spring Cache | 替换 |
| MQ | Kafka | RocketMQ | 适配 |
| ORM | MyBatis | JPA | 重写 |
| Auth | JWT | OAuth2 | 人工处理 |

---

# ⚠️ 迁移风险等级

| 等级 | 含义 |
|---|---|
| Low | 纯业务逻辑 |
| Medium | 需要工具替换 |
| High | 存在基础设施耦合 |
| Critical | 存在平台/runtime 差异 |

# ❌ 常见 AI 迁移失败案例

---

## Case 1 — AI 假设依赖存在

### 问题

AI 幻觉出不存在的工具类。

### 解决方案

必须先验证目标项目能力。

---

## Case 2 — 直接复制源项目架构

### 问题

AI 生搬硬套源实现。

### 风险

- 架构污染
- 技术债务
- Runtime 问题

### 解决方案

必须执行目标项目适配。

---

## Case 3 — 隐式基础设施耦合

### 问题

功能依赖：

- MQ
- Cache
- 分布式事务
- ThreadLocal
- 生命周期 Hook

### 解决方案

执行依赖分类分析。

---

## Case 4 — 框架适配错误

### 问题

AI 错误映射：

- ORM
- Auth
- DI
- Async

### 解决方案

先做兼容性验证。

# 👨‍⚖️ Human-in-the-Loop 原则

```text
AI 提供迁移方案。
人类负责架构决策。
```

AI 负责：

- 分析依赖
- 生成迁移方案
- 提供替代建议
- 辅助适配
- 识别风险

人类负责：

- 确认架构边界
- 确认兼容性
- 控制迁移范围
- 最终审核

---

# 📌 核心原则

## 1. 禁止盲迁移

必须先验证目标项目能力。

---

## 2. 不要整模块迁移

建议：

- 小功能
- 独立流程
- 小依赖范围

逐步迁移。

---

## 3. 保持目标项目架构

迁移功能：

不是迁移架构。

禁止将源项目模式强行带入目标项目。

---

## 4. 基础设施不是业务逻辑

不要直接迁移：

- MQ 实现
- Cache 框架
- ORM 框架
- 鉴权体系
- Thread Context

这些需要适配。
